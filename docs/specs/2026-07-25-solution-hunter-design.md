# solution-hunter — дизайн скила нон-стоп поиска решений

Дата: 2026-07-25. Статус: утверждён пользователем, ждёт план реализации.

## Задача

Скил, превращающий сессию Claude Code в непрерывный исследовательский цикл: пользователь задаёт задачу («стратегия иксов к депозиту $200»), процесс через субагентов генерирует идеи, комбинирует их, адверсариально перепроверяет и не останавливается, пока пользователь сам не скажет «стоп».

## Решение (выбранный подход)

Скил-оркестратор в плагине `fable-workflows` на базе механизма `/loop` (dynamic mode, ScheduleWakeup): раунд поиска → отчёт в чат → самопланируемое пробуждение через 20–30 мин → следующий раунд. Вся содержательная работа — в субагентах; состояние — в файлах, переживающих сжатие контекста.

Отклонённые альтернативы: один большой Workflow (конечен, нет вмешательства пользователя между раундами); отдельный агент-оркестратор (субагент не умеет планировать пробуждения и жить бесконечно).

## 1. Запуск и интейк

`/solution-hunter <задача>`. Перед стартом цикла скил фиксирует в `BRIEF.md`:

- цель;
- измеримый критерий «достаточно близко» (например «ожидаемый x2–x5 к $200 при просадке ≤ N%»);
- жёсткие ограничения (бюджет, риск, время);
- что считается доказательством (evidence-стандарт).

Если критерий неизмерим — скил задаёт уточняющие вопросы и не стартует, пока критерий не зафиксирован.

## 2. Файловое состояние

Каталог `~/research/<slug>/`:

| Файл | Содержимое |
|---|---|
| `BRIEF.md` | задача, критерии, ограничения |
| `LEDGER.md` | реестр всех идей: id, гипотеза, линза-источник, статус, скоринг, evidence |
| `CANDIDATES.md` | идеи, пережившие опровержение и прошедшие критерий BRIEF |
| `ROUNDS.md` | журнал раундов: новые/убитые идеи, использованные линзы, счётчик сухих раундов |

Статусы идей: `raw → combined → verified | refuted → candidate`. Убитые идеи остаются в LEDGER навсегда (для дедупа).

## 3. Раунд (средний профиль: ~8–12 субагентов, раз в 20–30 мин)

1. **Генерация** — 3–4 субагента на `sonnet`, каждый со своей линзой. Линзы ротируются между раундами из пула: аналогии из чужих доменов, инверсия («как гарантированно провалиться — и наоборот»), веб-разведка (WebSearch: что реально работает у других), contrarian, декомпозиция задачи.
2. **Комбинация** — один субагент скрещивает топ-идеи из LEDGER между собой (перебор комбинаций).
3. **Опровержение** — 2–3 критика по железному правилу critical-review: «нет находки без evidence». Каждый пытается убить идею фактом, числом, контрпримером; верификатор с WebSearch проверяет фактику. Идея без выжившего evidence не проходит дальше `raw`.
4. **Синтез** — оркестратор (основная модель): обновляет LEDGER, скорит, пишет в чат дельту раунда (новые / убитые / кандидаты), планирует следующее пробуждение через ScheduleWakeup.

## 4. Анти-застревание

- Дедуп новых идей против всего LEDGER, включая refuted (трупы не воскресают).
- 2 сухих раунда подряд (ничего нового) → принудительная смена линз + протокол getting-unstuck (поиск скрытого допущения, которое сужает пространство поиска).
- 4 сухих раунда → переформулировка задачи и явный вопрос пользователю.

## 5. Управление

- Цикл никогда не останавливается сам. При появлении кандидата, проходящего критерий BRIEF, — пометка в CANDIDATES.md и пинг пользователя; поиск продолжается.
- Пользователь в любой момент пишет в чат: «копай ветку N», «убей направление X», «стоп».
- «Стоп» → ScheduleWakeup(stop) + финальный сводный отчёт по всему LEDGER.

## 6. Экономия моделей

Генераторы — `sonnet`; механика (дедуп, ведение файлов) — `haiku`; критики и синтез — основная модель сессии. Субагенты не наследуют модель оркестратора там, где хватает уровня ниже.

## 7. Упаковка

- Новый скил `solution-hunter` в `plugins/fable-workflows/skills/`, на английском (как остальные скилы пака), с русскими триггерами в description: «ищи варианты нон-стоп», «перебирай идеи», «не останавливайся пока не найдёшь».
- Bump версии плагина + plugin update после мержа (по принятому процессу пака).
- Границы с соседями: critical-review — разовая проверка существующих материалов; getting-unstuck — ломка объявленного тупика; solution-hunter — непрерывный поиск нового с обоими как встроенными фазами.

## Тестирование

- Сухой прогон: задача с заведомо известным ответом — цикл должен найти и пометить кандидата, не остановившись.
- Проверка дедупа: подсунуть в LEDGER refuted-идею — генераторы не должны предложить её повторно как новую.
- Проверка стопа: слово «стоп» в любой фазе → финальный отчёт, ноль новых пробуждений.
