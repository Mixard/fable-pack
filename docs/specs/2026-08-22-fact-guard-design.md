# fact-guard — дизайн скила против выдуманных фактов о заказчике + расширение fable-guard

Дата: 2026-08-22. Статус: утверждён пользователем после критического ревью триажа nick-vels/autopilot (из 7 кандидатов на заимствование выжили два — единственные с задокументированной повторяющейся болью). Ждёт план реализации.

## Задача

Один и тот же класс ошибки зафиксирован в трёх проектах на сервере: агент подставляет правдоподобный, но выдуманный факт о заказчике или его домене — и он доезжает до артефакта.

- FIXMATE/DCWP-NYC: `procurement-known-fabrications.md` — 15 галлюцинированных фактов (несуществующий факс, перепутанный vendor code, неверные NIGP-коды, выдуманное имя президента компании, неверный email VA). Проект построил свой реестр + guard-агент вручную.
- Tonya_glam: «Lessons learned» в CLAUDE.md — выдуманный Instagram-хэндл, перепутанное имя продукта, неверный voice register.
- geo_rpg: `docs/CRITICAL_REVIEW.md` F19 — юридические и web3-цифры не проходили верификацию.

У нас `writing-plans` запрещает плейсхолдеры в *планах*, а `verification-before-completion` требует доказательств для *утверждений о статусе работы*. Ни один скил не говорит: «факт о заказчике не выдумывается; незнание — видимый плейсхолдер; однажды пойманная фабрикация заносится в реестр и больше не проходит».

Вторая, мелкая часть: хук `fable-guard` блокирует 10 паттернов секретов, но не знает Telegram bot-токен, Stripe live-ключи, JWT и connection-string с паролем — ровно те, что появятся в ближайших этапах geo_rpg (этап 2), tonya_club, telegram.

## Решение

### Часть 1. Скил `fable-workflows:fact-guard`

Однофайловый скил в стиле пакета (`SKILL.md`, ~120 строк, без агента и скриптов). Три правила и один артефакт.

**Правило 1 — плейсхолдер вместо выдумки.** Факт о заказчике (название, имя человека, телефон, адрес, email, хэндл, домен, цена, код/ID/лицензия, дата, юридический порог, цитата) либо взят из названного источника, либо стоит видимым плейсхолдером `[ТЕЛЕФОН — уточнить у владельца]`. Правдоподобная выдуманная цена хуже очевидного пробела. Плейсхолдеры собираются в одном списке «Что нужно от вас» в конце отчёта/артефакта — тот же приём, что в финальном отчёте autopilot.

**Правило 2 — источник истины проекта.** Если в проекте есть файл фактов (`shared/brand-facts.yaml`, `docs/channel-static.md`, `procurement-facts.yaml` — скил ищет по именам и по CLAUDE.md), он бьёт память агента всегда. Нет файла — скил предлагает завести `docs/facts.yaml` при первом же факте, который пришлось спрашивать у владельца.

**Правило 3 — реестр фабрикаций и проверка перед сдачей.** Артефакт `docs/known-fabrications.md` — таблица `# | выдуманное значение | откуда взялось | правильное значение | источник`, формат взят из FIXMATE/DCWP дословно. Любой пойманный выдуманный факт (ревью, владелец, самопроверка) — строка в реестр **в том же ходу**, не «потом». Перед сдачей любого артефакта с фактами о заказчике (текст, письмо, конфиг, лендинг, отчёт):

1. `grep -F` по левой колонке реестра — совпадение = FAIL, артефакт не сдаётся;
2. каждое число/код/контакт/имя в артефакте либо трассируется в файл фактов, либо помечено плейсхолдером — иначе NEEDS-SOURCE;
3. при сомнении — блокировать: перепроверка дешевле ошибки в письме клиенту.

Проверку делает сам агент инлайн для артефактов до ~2 страниц; больше — субагент на `haiku`/`sonnet` с путём к артефакту, реестру и файлу фактов (формат отчёта PASS / NEEDS-SOURCE / FAIL, как у `proc-fact-guard`).

**Триггеры в description:** любая работа с названиями, именами, контактами, ценами, кодами, лицензиями, датами и цитатами заказчика; черновики писем, лендингов, отчётов, карточек товаров, рекламных текстов; когда владелец говорит «откуда ты это взял», «это неправильно», «такого нет».

**Явно вне рамок:** верификация внешних фактов мира (версии библиотек, API) — это `freshness-sweep` и `verification-before-completion`; проверка кода на баги — `code-review`.

Альтернативы:

- **Агент `fable-agents:fact-guard`** вместо скила — отклонён: агенту нужны проектные пути к источникам истины, которые есть только у оркестратора; FIXMATE смог зашить пути в агента, потому что он проектный. Пакетный вариант — скил, который говорит оркестратору, что передать субагенту.
- **Раздел в `verification-before-completion`** — отклонён: тот скил про «команда доказывает статус», у него другой триггер; смешение размоет оба.
- **Заимствовать манифест требований autopilot целиком** — отклонён: ни одного задокументированного случая потерянного требования в 13 репо; это вес под несуществующую проблему.

### Часть 2. Патч `fable-guard/hooks/guard.py`

Добавить в `SECRET_PATTERNS` четыре записи:

| Паттерн | Что ловит | Риск ложных срабатываний |
|---|---|---|
| `\b\d{8,10}:[A-Za-z0-9_-]{35}\b` | Telegram bot-токен | низкий: форма уникальна |
| `\b(?:sk\|rk)_live_[A-Za-z0-9]{20,}` | Stripe live secret/restricted key | низкий; `sk_test_` намеренно **не** блокируем — тестовые ключи в доках и фикстурах легитимны |
| `\beyJ[A-Za-z0-9_-]{10,}\.eyJ[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}\b` | JWT (три сегмента, заголовок+payload в base64url-JSON) | средний: JWT встречаются в тестах; принимаем — в Write/Edit реальный токен встречается чаще, чем фикстура, и отказ объясняет причину |
| `\b(?:postgres(?:ql)?\|mysql\|mongodb(?:\+srv)?\|redis\|amqp)://[^\s/:@]+:[^\s@]+@` | connection-string с паролем | низкий: URL без пароля (`user@host`) не матчится |

Тесты в `plugins/fable-guard/test_guard.py`: по одному позитивному и одному негативному кейсу на паттерн (для Stripe негатив — `sk_test_`; для connection-string — URL без пароля; для JWT — двухсегментная строка).

## Версии и релиз

- `fable-workflows` 1.2.0 → **1.3.0** (новый скил), `fable-guard` 0.4.0 → **0.5.0** (новые паттерны = новое поведение блокировки, не багфикс).
- CHANGELOG, README пакета (таблица скилов), `scripts/validate.py` — через скил `release`.
- Обновить `fable-workflows/skills/verification-before-completion` и `writing-plans` одной перекрёстной ссылкой на `fact-guard` («факты о заказчике — см. fact-guard») — две строки, не больше.

## Критерии приёмки

1. `scripts/validate.py` зелёный; `test_guard.py` зелёный с новыми кейсами.
2. Прогон скила на FIXMATE/DCWP: скил находит существующий `procurement-known-fabrications.md` как реестр (по имени-паттерну `*known-fabrications*`) и при проверке черновика с «Trevor Wilson» возвращает FAIL.
3. Прогон на geo_rpg: в артефакте с выдуманной ценой подписки скил ставит плейсхолдер и выносит его в «Что нужно от вас».
4. Ни один из четырёх новых паттернов не срабатывает на текущих tracked-файлах 13 репо сервера (`git grep -E` по каждому — ноль совпадений вне заведомых примеров).

## Открытые места

Нет. Кандидаты, отклонённые на ревью (requirements-manifest, context-handoff, апгрейды SDD, Unity-knowledge), зафиксированы в этом документе как «вне рамок» и не возвращаются без нового доказательства нужды.
